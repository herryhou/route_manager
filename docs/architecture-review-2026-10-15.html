Problem. rm-edit is shallow: plan functions are 20-line field-copies while the semantics that break (in-tx revalidation, bearing carry, stale marks) live in rm-db — the crate seam splits every edit primitive load→plan→apply with no locality.

Solution. Fold plan policy into rm-db beside its apply counterpart; each edit primitive becomes one module behind one interface. Handlers call rm-db directly.

  • locality: edit lifecycle in one module
  • delete 1:1 error enum + 2 mappers
  • delete ~6 pass-through structs per rename
  • leverage: one interface, tests already DB-backed

Deletion test: delete rm-edit → complexity concentrates in rm-db. Passes hardest of all seven.

Problem. The response shape — the real interface between query code and the page — is declared by hand three times (SQL column order, json!() literals, JS property access), so the compiler guards none of it, and it has already drifted once inside queries/stops.rs.

Solution. Each endpoint response becomes a named serde struct in the query module: column order, JSON keys, and JS expectations get one definition.

  • compiler guards the hottest seam in the repo

  • JS gains a reference shape to read against

Problem. The stale-mark protocol — the invariant behind “never green over stale data” — has no home: writers name tables by magic string, three pipeline crates each re-implement the SELECT / rebuild / guarded-DELETE loop, and the UI re-encodes the keying convention in ad-hoc SQL at the presentation layer.

Solution. One rm-db-owned stale-mark module (mark, marks_for, clear_if_unchanged); the three run_stale loops shrink to load marks → call the existing rebuild → clear.

  • freshness rule enforced in one place
  • locality: protocol change lands once
  • delete 2 verbatim loops + 2 EXISTS copies
  • table names become constants, not strings

Problem. app.js is a god-module: ~12 concerns, and the entity-specific flows are hand-copies — the exact code the 59-commit churn keeps landing on, untestable by construction (include_str!-compiled, no JS test infra).

Solution. Extract the three duplicated skeletons (log, undo, select) so each exists once with the entity as an argument; then split remaining concerns along the seams the file already has.

  • leverage: one skeleton, three entities
  • locality: undo fix lands once
  • hottest churn stops multiplying copies
  • seams become testable without a framework

Constraint to weigh in grilling: no JS test infra exists — skeletons can be extracted, but verifying behavior stays manual unless the extraction itself adds a harness.

Problem. One undo endpoint returns a union of three response shapes whose discriminant the client must already know; unknown entities deliberately fall down the stop branch so their error surfaces as its 409 — even error-path semantics depend on the leak.

Solution. One tagged outcome ({edit_id, kind, restored_version_id, override_deleted?}) serialized uniformly; the handler branch and the JS per-entity response knowledge both delete.

  • dispatch deletes at both ends of the seam
  • error paths stop depending on the leak
  • undo flows collapse onto №4's skeleton

Top recommendation

№1 — Collapse the rm-edit module into rm-db

Deletion test passes hardest: a whole crate of pass-throughs, a duplicated error enum, and ~10 structs per rename all concentrate into rm-db's already-deep apply_* implementation. Existing DB-backed tests cross the same interface either way, so the net exists before you touch anything — and it shrinks the seam the edit-flow churn (handlers/edit.rs, 14 commits) keeps crossing. №2 is the bigger long-term leverage on the hottest area; it deserves the grilling loop and maybe design-it-twice before committing to a shape.
